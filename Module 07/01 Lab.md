## 6. Создание равномерно распределённого набора данных

Создадим таблицу заказов. В качестве ключа распределения используем
уникальный `order_id`.

``` sql
CREATE TABLE lab8.sales_uniform
(
    order_id    BIGINT,
    customer_id INTEGER,
    product_id  INTEGER,
    quantity    INTEGER,
    amount      NUMERIC(12,2),
    created_at  TIMESTAMP
)
DISTRIBUTED BY (order_id);
```

Сгенерируйте 200 000 строк:

``` sql
INSERT INTO lab8.sales_uniform
SELECT
    gs,
    (gs % 10000)::INTEGER + 1,
    (gs % 500)::INTEGER + 1,
    (gs % 10)::INTEGER + 1,
    ((gs % 100000)::NUMERIC / 100 + 10)::NUMERIC(12,2),
    TIMESTAMP '2025-01-01 00:00:00' + gs * INTERVAL '1 second'
FROM generate_series(1, 200000) AS gs;
```

Проверьте количество строк:

``` sql
SELECT COUNT(*) AS total_rows
FROM lab8.sales_uniform;
```

Проверьте распределение строк по сегментам:

``` sql
SELECT
    gp_segment_id,
    COUNT(*) AS rows_count
FROM lab8.sales_uniform
GROUP BY gp_segment_id
ORDER BY gp_segment_id;
```

**Задание 2.**

1.  Сохраните количество строк на каждом сегменте.
2.  Определите, насколько равномерно распределены данные.
3.  Объясните, почему уникальный и достаточно равномерный ключ обычно
    подходит для `DISTRIBUTED BY`.

## 7. Создание таблицы с перекосом данных (data skew)

Создадим таблицу, в которой большая часть строк имеет одинаковое
значение ключа распределения:

``` sql
CREATE TABLE lab8.sales_skew
(
    order_id    BIGINT,
    skew_key    INTEGER,
    amount      NUMERIC(12,2)
)
DISTRIBUTED BY (skew_key);
```

Заполните таблицу: для 90% строк `skew_key` будет равен 1.

``` sql
INSERT INTO lab8.sales_skew
SELECT
    gs,
    CASE
        WHEN gs <= 90000 THEN 1
        ELSE gs
    END,
    (gs % 100000)::NUMERIC / 100
FROM generate_series(1, 100000) AS gs;
```

Посмотрите распределение:

``` sql
SELECT
    gp_segment_id,
    COUNT(*) AS rows_count
FROM lab8.sales_skew
GROUP BY gp_segment_id
ORDER BY gp_segment_id;
```

Сравните результат с таблицей `sales_uniform`.

**Задание 3.**

1.  Определите сегмент, на который пришлось наибольшее количество строк.
2.  Объясните, почему одинаковое значение ключа распределения приводит к
    концентрации строк на одном сегменте.
3.  Опишите, как перекос данных может повлиять на время выполнения
    распределённых запросов.

## 10. Resource Queues: ограничение параллельных запросов

### 10.1. Проверка режима менеджера ресурсов

Выполните:

``` sql
SHOW gp_resource_manager;
```

Продолжайте этот раздел только если результат показывает режим `queue`.

Если используется `group`, не переключайте режим в рамках лабораторной.
Вместо этого изучите теоретическое назначение Resource Queues и
зафиксируйте текущий режим.

### 10.2. Создание очереди

Под пользователем с административными правами создайте очередь:

``` sql
CREATE RESOURCE QUEUE lab8_queue
WITH (ACTIVE_STATEMENTS = 2);
```

Создайте учебную роль:

``` sql
CREATE ROLE lab8_user LOGIN RESOURCE QUEUE lab8_queue;
```

Задайте пароль интерактивно:

``` sql
\password lab8_user
```

Не используйте в отчёте реальный пароль.

### 10.3. Проверка ограничения

Откройте три отдельных терминала на Coordinator. В каждом подключитесь к
базе от имени `lab8_user`:

``` bash
psql -h <coordinator-host> -U lab8_user -d gp_lab8
```

В каждой из трёх сессий запустите:

``` sql
SELECT pg_sleep(45);
```

Поскольку для очереди установлено `ACTIVE_STATEMENTS = 2`, одновременно
исполняться должны не более двух запросов этой роли, а дополнительный
запрос может ожидать освобождения слота.

Во время выполнения запросов откройте административную сессию и
проверьте:

``` sql
SELECT *
FROM gp_toolkit.gp_resqueue_status;
```

Также выполните:

``` sql
SELECT *
FROM gp_toolkit.gp_resq_activity;
```

Если представление показывает ожидающие запросы, найдите очередь
`lab8_queue` и зафиксируйте наблюдения.

> **Критически важно:** проверочные запросы запускайте именно от имени
> `lab8_user`. Суперпользовательские сессии могут обходить обычные
> ограничения Resource Queue, поэтому они не подходят для этой
> демонстрации.

### 10.4. Очистка объектов Resource Queue

После завершения тестов удалите учебную роль и очередь:

``` sql
DROP ROLE lab8_user;
DROP RESOURCE QUEUE lab8_queue;
```

Если роль ещё владеет объектами или имеет активные подключения, сначала
завершите тестовые сессии и устраните зависимости штатным способом.

## 11. Greenplum Command Center (GPCC)

Greenplum Command Center --- отдельный компонент мониторинга и
управления Greenplum. В зависимости от версии и установки он
предоставляет веб-интерфейс для просмотра состояния кластера, запросов,
нагрузки и использования ресурсов.

GPCC может не входить в установленный учебный стенд. Не устанавливайте и
не перенастраивайте его самостоятельно в рамках этой лабораторной.

Проверьте, есть ли связанные процессы или службы:

``` bash
ps -ef | grep -i '[g]pcc'
```

При наличии systemd-службы можно посмотреть её статус, если её имя
известно из документации конкретной установки:

``` bash
systemctl list-units --type=service | grep -i gpcc
```

Если преподаватель предоставил адрес веб-интерфейса GPCC, откройте его в
браузере.

Изучите доступные разделы, если они присутствуют:

-   общее состояние кластера;
-   состояние сегментов;
-   активные и завершённые запросы;
-   длительные запросы;
-   использование ресурсов;
-   история нагрузки.

**Задание 7.** Перечислите три задачи администратора, для которых GPCC
удобнее, чем ручной просмотр отдельных SQL-представлений и логов.

Если GPCC отсутствует, укажите это в отчёте и опишите его назначение по
документации.

## 12. Greenplum Workload Manager (GP-WLM)

Greenplum Workload Manager --- отдельный компонент управления рабочей
нагрузкой. Его возможности и способ интеграции зависят от конкретной
поставки и версии.

Проверьте, доступна ли утилита:

``` bash
command -v gp-wlm
```

Если команда найдена, выведите справку:

``` bash
gp-wlm --help
```

При наличии соответствующих процессов можно выполнить:

``` bash
ps -ef | grep -i '[w]lm'
```

В рамках этой лабораторной не изменяйте политики WLM и не запускайте
команды, ограничивающие или завершающие пользовательские запросы.

## 13. Утилиты менеджмента и обслуживания Greenplum

В этом разделе изучается назначение утилит. Запускаются только
безопасные команды просмотра справки и конфигурации.

### 13.1. gpconfig

Посмотрите значение одного из параметров конфигурации:

``` bash
gpconfig -s gp_resource_manager
```

Для просмотра справки:

``` bash
gpconfig --help
```

`gpconfig` предназначена для просмотра и управления конфигурационными
параметрами Greenplum на Coordinator и сегментах. Изменение параметров в
лабораторной не выполняется.

### 13.2. gpcheckperf

Посмотрите справку:

``` bash
gpcheckperf --help
```

Утилита предназначена для оценки производительности и пропускной
способности инфраструктуры кластера. Полноценные тесты могут создавать
заметную нагрузку и требуют согласования с администратором.

### 13.3. gpcheckcat

Посмотрите справку:

``` bash
gpcheckcat --help
```

Утилита предназначена для проверки согласованности системного каталога
Greenplum. Диагностические и исправляющие режимы следует применять
только по регламенту и после резервного копирования/оценки риска.

### 13.4. gprecoverseg

Посмотрите справку:

``` bash
gprecoverseg --help
```

Утилита используется для восстановления сегментов. В этой лабораторной
её не запускают на восстановление: для этого необходим реальный сценарий
отказа, подготовленный стенд и разрешение администратора.

**Задание 9.** Для каждой из четырёх утилит (`gpconfig`, `gpcheckperf`,
`gpcheckcat`, `gprecoverseg`) укажите назначение и пример ситуации, в
которой администратор может её использовать.

## 14. Итоговый сценарий диагностики

Представьте, что пользователи сообщили о замедлении выполнения
аналитических запросов.

Выполните последовательность проверок:

    ``` sql

    FROM gp_segment_configuration
    ORDER BY content, role;
    ```

3.  Проверить текущий менеджер ресурсов:

    ``` sql
    SHOW gp_resource_manager;
    ```

4.  Проверить распределение тестовых данных:

    ``` sql
    SELECT gp_segment_id, COUNT(*)
    FROM lab8.sales_uniform
    GROUP BY gp_segment_id
    ORDER BY gp_segment_id;
    ```

5.  Проверить таблицу с перекосом:

    ``` sql
    SELECT gp_segment_id, COUNT(*)
    FROM lab8.sales_skew
    GROUP BY gp_segment_id
    ORDER BY gp_segment_id;
    ```

6.  Посмотреть план проблемного запроса с помощью `EXPLAIN ANALYZE`.

7.  При доступности изучить представления `gp_toolkit` и интерфейс GPCC.

**Итоговое задание.** Составьте краткий план диагностики, в котором
разделите возможные причины замедления на три группы:

-   состояние инфраструктуры и сегментов;
-   перекос данных и особенности плана запроса;
-   конкуренция запросов за ресурсы.

Не выполняйте восстановление сегментов, изменение конфигурации или
принудительное завершение запросов.
