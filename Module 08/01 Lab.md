# Часть 1. Аутентификация клиентов

## 5. Изучение pg_hba.conf

`pg_hba.conf` определяет, каким клиентам разрешено подключаться к базе,
под какой ролью и каким способом они проходят аутентификацию.

### 5.1. Определение расположения файла

Выполните:

``` sql
SHOW data_directory;
```

Проверьте параметр пути к HBA-файлу, если он поддерживается данной
сборкой:

``` sql
SHOW hba_file;
```

Если `hba_file` не распознаётся, используйте каталог данных и
документацию установленной версии. На Coordinator можно проверить
наличие файла:

``` bash
ls -l <data_directory>/pg_hba.conf
```

Посмотрите содержимое файла только для чтения:

``` bash
sed -n '1,200p' <data_directory>/pg_hba.conf
```

Не публикуйте содержимое файла целиком, если в нём присутствуют
внутренние адреса или другие сведения об инфраструктуре.

### 5.2. Разбор правил

Стандартная структура правила:

``` text
TYPE  DATABASE  USER  ADDRESS  METHOD
```

Пример:

``` text
host    gp_lab_security    lab_reader    192.168.10.0/24    md5
```

Разберите поля:

-   `host` --- тип подключения;
-   `gp_lab_security` --- база данных;
-   `lab_reader` --- роль;
-   `192.168.10.0/24` --- разрешённая сеть клиента;
-   `md5` --- метод аутентификации.

Типы правил, которые следует знать:

  Тип           Назначение
  ------------- -----------------------------------------
  `local`       Локальное подключение через Unix socket
  `host`        TCP-подключение
  `hostssl`     TCP-подключение с SSL
  `hostnossl`   TCP-подключение без SSL

Порядок записей важен: применяется первое подходящее правило.

### 5.3. Определение метода аутентификации

Найдите в файле все активные правила и выпишите:

-   какие правила разрешают локальные подключения;
-   какие разрешают TCP-подключения;
-   какие методы аутентификации используются;
-   есть ли правила с `trust`;
-   ограничены ли клиентские адреса конкретными подсетями;
-   используются ли правила `hostssl`.

Комментарии, начинающиеся с `#`, не являются активными правилами.

### 5.4. Проверка фактического подключения

Из клиентской машины или отдельной сессии выполните подключение к
Coordinator:

``` bash
psql -h <coordinator-host> -p <coordinator-port> \
     -U <existing_test_user> -d <existing_test_database>
```

После подключения выполните:

``` sql
SELECT
    current_user,
    session_user,
    current_database(),
    inet_client_addr(),
    inet_server_addr();
```

# Часть 2. Настройка авторизации

## 6. Создание учебной базы и объектов

В этой части создаются отдельная база, схема, таблица и учебные роли.

### 6.1. Создание базы

Под административной учётной записью выполните:

``` sql
CREATE DATABASE gp_lab_security;
```

Подключитесь к ней:

``` sql
\c gp_lab_security
```

Создайте схему и таблицу:

``` sql
CREATE SCHEMA security_lab;

CREATE TABLE security_lab.customers
(
    customer_id INTEGER PRIMARY KEY,
    customer_name VARCHAR(100),
    city VARCHAR(80),
    credit_limit NUMERIC(12,2)
)
DISTRIBUTED BY (customer_id);
```

Добавьте тестовые строки:

``` sql
INSERT INTO security_lab.customers
VALUES
    (1, 'Customer One', 'Almaty', 10000.00),
    (2, 'Customer Two', 'Astana', 15000.00),
    (3, 'Customer Three', 'Karaganda', 7000.00);
```

Проверьте данные:

``` sql
SELECT * FROM security_lab.customers ORDER BY customer_id;
```

### 6.2. Создание ролей

Создайте три роли для разных задач:

``` sql
CREATE ROLE sec_reader LOGIN;
CREATE ROLE sec_writer LOGIN;
CREATE ROLE sec_manager LOGIN;
```

Задайте пароли интерактивно из `psql`:

``` sql
\password sec_reader
\password sec_writer
\password sec_manager
```

Используйте разные учебные пароли. Не помещайте пароли в отчёт или
SQL-файл.

Разрешите подключение к базе:

``` sql
GRANT CONNECT ON DATABASE gp_lab_security
TO sec_reader, sec_writer, sec_manager;
```

Разрешите использование схемы:

``` sql
GRANT USAGE ON SCHEMA security_lab
TO sec_reader, sec_writer, sec_manager;
```

### 6.3. Назначение минимальных привилегий

Роль `sec_reader` должна только читать данные:

``` sql
GRANT SELECT ON security_lab.customers
TO sec_reader;
```

Роль `sec_writer` должна читать и добавлять строки:

``` sql
GRANT SELECT, INSERT ON security_lab.customers
TO sec_writer;
```

Роль `sec_manager` в этой учебной модели получает возможность читать и
изменять данные:

``` sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON security_lab.customers
TO sec_manager;
```

Не выдавайте этим ролям `SUPERUSER`, `CREATEDB` или `CREATEROLE`.

### 6.4. Проверка привилегий

Посмотрите выданные права:

``` sql
SELECT
    grantee,
    table_schema,
    table_name,
    privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'security_lab'
ORDER BY grantee, table_name, privilege_type;
```

Посмотрите атрибуты ролей:

``` sql
SELECT
    rolname,
    rolsuper,
    rolcreatedb,
    rolcreaterole,
    rolcanlogin
FROM pg_roles
WHERE rolname IN ('sec_reader', 'sec_writer', 'sec_manager')
ORDER BY rolname;
```

# Часть 3. Аудит

## 9. Изучение параметров журналирования

Аудит позволяет определить, кто подключался к системе, какие действия
выполнял и когда это происходило.

Сначала изучите текущие параметры журналирования:

``` sql
SELECT
    name,
    setting,
    unit,
    source
FROM pg_settings
WHERE name IN (
    'logging_collector',
    'log_directory',
    'log_filename',
    'log_connections',
    'log_disconnections',
    'log_statement',
    'log_min_duration_statement'
)
ORDER BY name;
```

Также можно проверить отдельные параметры:

``` sql
SHOW logging_collector;
SHOW log_directory;
SHOW log_filename;
SHOW log_connections;
SHOW log_disconnections;
SHOW log_statement;
SHOW log_min_duration_statement;
```

Если отдельный параметр отсутствует в вашей сборке, зафиксируйте это и
проверьте документацию для установленной версии.

# Часть 4. Шифрование данных и сетевых соединений

## 14. Проверка TLS/SSL на Coordinator

TLS защищает сетевой трафик между клиентом и сервером. Для полноценной
проверки подлинности сервера клиент должен проверять сертификат, а не
просто устанавливать зашифрованное соединение.

Посмотрите параметры:

``` sql
SHOW ssl;
SHOW ssl_cert_file;
SHOW ssl_key_file;
SHOW ssl_ca_file;
```

Если параметр отсутствует в конкретной сборке, зафиксируйте это и
проверьте документацию установленной версии.

Проверьте, доступно ли представление SSL-сессий:

``` sql
SELECT *
FROM pg_stat_ssl;
```

Если представление доступно, сопоставьте его с активными соединениями:

``` sql
SELECT
    a.pid,
    a.usename,
    a.datname,
    a.client_addr,
    s.ssl,
    s.version,
    s.cipher
FROM pg_stat_activity a
LEFT JOIN pg_stat_ssl s
    ON a.pid = s.pid
ORDER BY a.usename, a.pid;
```

Если `pg_stat_ssl` отсутствует или отдельные столбцы недоступны, не
пытайтесь создавать их самостоятельно: зафиксируйте ограничение
версии/сборки.

## 15. Проверка клиентского подключения

В `psql` выполните:

``` text
\conninfo
```

Команда показывает сведения о текущем соединении. В зависимости от
версии клиента и способа подключения в выводе может быть указано,
используется ли SSL.

Если TLS уже настроен администратором, выполните тестовое подключение с
проверкой сертификата. Пример для клиента `psql`:

``` bash
psql "host=<coordinator-fqdn> port=<coordinator-port> \
dbname=gp_lab_security user=sec_reader \
sslmode=verify-full sslrootcert=<path-to-ca-certificate>"
```

Для `verify-full` имя узла должно соответствовать имени в сертификате, а
CA-сертификат должен быть доверенным.

Если TLS на стенде не настроен, не пытайтесь включить его изменением
файлов в ходе этой лабораторной. Зафиксируйте текущий статус и составьте
план внедрения.

## 17. Шифрование данных при хранении

Шифрование данных при хранении (at rest) защищает файлы БД и резервные
копии при физическом доступе к носителям или утечке файлов.

В этой лабораторной необходимо исследовать архитектуру защиты, а не
включать шифрование на работающем кластере.

На каждом Segment Host и Coordinator (при наличии разрешённого доступа)
выполните:

``` bash
lsblk -f
```

Посмотрите точки монтирования:

``` bash
findmnt
```

Проверьте наличие устройств с типом `crypto_LUKS` в выводе `lsblk -f`.

Ответьте:

-   используются ли зашифрованные блочные устройства;
-   где расположены каталоги данных Greenplum;
-   защищены ли тома с данными;
-   где хранятся резервные копии;
-   зашифрованы ли резервные копии и как защищаются ключи.

Наличие LUKS-раздела само по себе не доказывает, что именно на нём
находятся данные Greenplum: сопоставьте устройство с точкой монтирования
и каталогом данных.

## 18. Защита резервных копий

Резервные копии могут содержать полный набор данных, поэтому к ним
применяются требования не ниже, чем к самой базе.

Составьте схему защиты резервных копий:

-   шифрование до передачи в удалённое хранилище;
-   отдельное хранение ключей;
-   ограничение доступа к хранилищу;
-   защищённый канал передачи;
-   контроль целостности;
-   регулярная проверка восстановления;
-   установленный срок хранения.

Не создавайте и не перемещайте реальные резервные копии без разрешения
преподавателя.

Удалите учебную базу:

``` sql
DROP DATABASE gp_lab_security;
```

Затем удалите учебные роли:

``` sql
DROP ROLE sec_reader;
DROP ROLE sec_writer;
DROP ROLE sec_manager;
```

Если роли имеют зависимости или активные подключения, сначала завершите
учебные сессии и устраните зависимости штатным способом. Не используйте
`CASCADE` без понимания последствий.

Если преподаватель планирует проверять результаты, не удаляйте объекты
до получения разрешения.
